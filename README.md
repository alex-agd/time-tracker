# Учёт рабочего времени

Веб-приложение для учёта рабочего времени сотрудников:

- добавление сотрудников;
- запуск и остановка таймера с описанием задачи;
- просмотр записей и общего времени каждого сотрудника за выбранный период;
- данные хранятся в PostgreSQL и сохраняются после перезапуска.

Все данные в проекте вымышленные.

**Стек:** Java 25, Spring Boot 4.1, Spring Data JPA, Flyway, PostgreSQL 18 · React 19, TypeScript, RTK Query, Tailwind 4, shadcn/ui.

## Запуск

Нужен только Docker:

```bash
docker compose up --build
```

- приложение: http://localhost:3000
- Swagger UI: http://localhost:8080/swagger-ui.html

При старте загружаются демо-данные (три вымышленных сотрудника). Чтобы начать с пустой базы, уберите `classpath:db/demo` из `FLYWAY_LOCATIONS` в `docker-compose.yml` и выполните `docker compose down -v`.

Запуск без Docker для разработки (нужны JDK 25 и Node 22):

```bash
docker compose up -d postgres
cd backend && ./mvnw spring-boot:run
cd frontend && npm ci && npm run dev
```

## ИИ-инструменты и модели

- **Claude Code** (CLI-агент) с моделью **Claude Opus 5.5** — проектирование, код бэкенда и фронтенда, тесты, Docker и CI.
- **Субагенты Claude Code** (та же модель) — параллельная сборка каркаса фронтенда и независимое ревью бэкенда.

Как работал с ИИ: сначала согласовывал стек и модель данных, затем принимал код небольшими шагами. Каждый шаг проверялся тестами, сборкой и ручным прогоном в браузере. Ошибки из раздела ниже находились именно на этих проверках.

### Примеры запросов

> Спроектируй модель данных и REST API для учёта рабочего времени: сотрудники, таймер с описанием задачи, отчёт по каждому сотруднику за период. У сотрудника не может быть больше одного запущенного таймера — даже при одновременных запросах.

> Напиши интеграционные тесты на реальном PostgreSQL: повторный запуск таймера, остановка без запуска, пустой отчёт, запись на границе периода, сохранение данных после перезапуска приложения.

> Отчёт за период считай одним SQL-запросом: запись, которая пересекает границу периода, учитывай только в его пределах, а запущенный таймер — до текущего момента.

> Сделай ревью бэкенда: транзакции, гонки, обработка ошибок, безопасность. По каждой найденной проблеме — тест, который её воспроизводит.

## Найденные и исправленные ошибки

1. **Сотрудник без записей получал в отчёте весь период.** В PostgreSQL `GREATEST`/`LEAST` игнорируют `NULL`, поэтому при `LEFT JOIN` без записей `GREATEST(NULL, :from)` давал `:from`, и в сумму попадала длина всего периода (86400 с вместо 0). Поймал тест пустого отчёта. Исправлено через `SUM(...) FILTER (WHERE t.id IS NOT NULL)`.
2. **Гонка при остановке таймера.** Два одновременных запроса на остановку оба получали 200, и второй перезаписывал время окончания. Нашлось на ревью; тест воспроизвёл ошибку (8 успешных остановок из 8). Исправлено блокировкой строки (`PESSIMISTIC_WRITE`).
3. **Таймер не запускался.** Метод репозитория `findByEmployeeIdAndEndedAtIsNull` Spring Data разбирал как обращение к несуществующему полю `employeeId`, хотя это связь `employee.id`. Заменено явным JPQL-запросом.
4. **Любая ошибка БД выдавалась за «таймер уже запущен».** Теперь в 409 превращается только нарушение уникального индекса активного таймера, остальные ошибки логируются и возвращаются как 500.
5. **Тест перезапуска подключался не к той базе.** Свойства, переданные через `SpringApplicationBuilder.properties()`, имеют самый низкий приоритет и перекрывались `application.yml`. Исправлено передачей аргументами командной строки.
6. **Боковое меню перекрывало контент.** Компонент shadcn был написан в синтаксисе Tailwind 3 (`w-[--sidebar-width]`), который не работает в Tailwind 4. Нашлось при ручной проверке, исправлено на `w-(--sidebar-width)`.
7. **Проект не собирался:** Spring Initializr вернул версию `4.1.2.RELEASE`, а артефакт называется `4.1.2`.
